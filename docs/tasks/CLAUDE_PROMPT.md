## 1. Реальний стан, який треба виправити

Наявний backend містить `backend/domain/matching.py` з дискретними `S/F/U` та старою формулою відповідності, `backend/domain/adaptive.py` з лексикографічним пріоритетом; `backend/api/catalog.py` формує знімок на основі ручного списку вакансій, `backend/api/interviews.py` підтримує банк multiple-choice, а відповіді у вільній формі не створюють прийнятої професійної оцінки. `backend/providers/llm.py` уже має початкові інтеграції Anthropic/OpenAI-compatible, але не завершений цикл rubric-based assessment. `backend/models.py` і міграції містять базову схему та розширення pgvector. У `frontend/src/App.tsx` є неправильний шлях `freezeAndStart()`, helper `u(...)` з транслітерації, безпідставні відсотки професійної відповідності та неузгоджені екрани.

Початкова база даних містить 90 **вигаданих, але структурованих** вакансій: Python, маркетинг, дизайн (по 30). Це важливий локальний набір даних. Не видаляй його, не видавай за реальні актуальні вакансії та не вигадуй роботодавцям активних посилань. У репозиторії є автентифікація, права доступу, частина інтерв'ю, UI та тести — збережи все корисне замість тотального переписування.

## 2. Єдиний продуктовый сценарій

**Авторизація → Вітання → Профіль → Одне адаптивне інтерв'ю → Рекомендації / оцінки / профіль ринку → після першого результату особисті вкладки.**

- До завершення першого процесу не показувати багатосторінкову панель із вкладками «вакансії», «налаштування» тощо. Профіль має поля: ім'я, спеціалізація, не від'ємні роки досвіду, локація, remote/hybrid/office, інші чітко позначені вподобання, власна оцінка **кожної обраної професійної дії**, а НЕ кожного пункту її рубрики. Власні оцінки можна редагувати; оцінки LLM — ні.
- Після профілю **сервер сам обирає всі релевантні валідні вакансії** з каталогу за справді жорсткими фільтрами. Досвід «5 років» не означає, що посада з мінімумом «3 роки» гірше підходить; перевищення мінімуму не штрафується. За відсутності достатніх даних не відхиляй вакансії як несумісні автоматично. Кандидат НЕ обирає вакансії перед співбесідою.
- Заморозити список вакансій і точні версії вимог (або повний JSON із ними), політику відбору та хеш. Цей snapshot є спільним для інтерв'ю та всіх подальших результатів — ніякої тихої зміни відбору посеред розмови.
- В інтерв'ю: **до десяти різних професійних дій** та **до п'яти фактично показаних запитань на одну дію**, зазвичай достатньо 1–2. Кожне питання відкрите, кандидат відповідає текстом. Бюджет — верхня межа, не план обов'язково запитати 50 разів. Збереження, відновлення, пропуск, завершення, зрозуміла обробка API-помилок і відсутнього LLM.
- Після результату: профіль зі списком дій і критеріями, редагована власна оцінка поруч з не редагованою LLM, ранжований список вакансій з поясненням і **таблиця профілю ринку**, відсортована за поширеністю компетентності. **Не показуй `40 із 40`, частки чи відсоток попиту**; лише порядок, назви й, за потреби, статус оцінювання. Далі розблокувати «Рекомендації», «Усі вакансії», «Мій профіль», «Налаштування».
- Ніколи не показувати старі `Match/Coverage/R`, великі «100% підходить», а також число, що видає себе за ймовірність працевлаштування. Рейтинг розраховується сервером детерміновано, а не пишеться LLM.

## 3. Математичне ядро — реалізуй буквально

Винеси чисті математичні функції з API та ORM в типізовані domain modules.

### Вакансії і ринковий профіль

`V_p={v∈V:H(v,p)=1}`. Для компетентності-дії `c`:

- `F(c) = (1/|V_p|) Σ_v 1[c∈C_v]`, де одна вакансія рахується лише один раз; батьківські технологічні поняття агрегуються теж за **унікальними ID вакансій**.
- `w_vg = 1/(|V_p|·|G_v|)`, де кожна вакансія робить рівний сумарний внесок.
- `I(c)=Σ_v Σ_g w_vg · 1[c∈A_vg]/|A_vg|` — альтернативи OR розділяють масу однієї групи; сума `I(c)` за валідних непорожніх дій дорівнює 1.
- **UI профілю ринку** впорядковує `F DESC → I DESC → stable ID ASC`. Не замінюй `F` вагами `I` і не відображай знаменник у UI.

### Планувальник

`Q_t(T)=Σ_v Σ_g w_vg·u_t(v,g)·1[T∩A_open(t,v,g)≠∅]` для ще невирішених груп з урахуванням OR. На кожній межі тем обирай `argmax_c Q_t({c})-Q_t(∅)`, при рівності: найбільше відкритих обов'язкових груп → потреба перевірки самооцінки / суперечності → `I(c)` → стабільний ID. Після завершення серії оцінювання перерахуй відкриті групи. Задоволена альтернатива OR закриває цю групу для цілей відповідної вакансії. Ні самозаявлений експертний рівень, ні самозаявлений 0 самі по собі не закривають тему. Статична гарантія greedy для submodular coverage не є гарантією точності всього інтерв'ю.

### Два LLM-контракти

- **Interviewer**: вибрана дія, рубрика та її версія, нез'ясовані критерії, контекст попередніх відповідей, мета наступного уточнення. Повертає одне природне ситуаційне питання українською. Не змінює обрану дію і ліміти.
- **Evaluator**: ВСІ збережені питання-відповіді поточної дії, ідентифікатори turns, рубрика і версія. Повертає **заново узагальнену оцінку критеріїв** `s_cd∈[0,1]∪{null}`, обґрунтування з точним `turn_id` і цитатою з реальної відповіді, `sufficient_evidence`, `needs_followup`, конкретну тему уточнення. Оцінки від різних запитань НЕ можна усереднювати механічно; нова оцінка ревізує попередню для поточної дії. `0` — оцінений негативний результат, `null` — свідчень бракує. Шкала рубрики: `[0,.25)` / `[.25,.50)` / `[.50,.75)` / `[.75,.90)` / `[.90,1]`, описана конкретними професійними anchors для дії. `0.78` не є вірогідністю.
- Backend перевіряє schema, дозволені criterion IDs, скінченні значення від 0 до 1, `null`, наявність дослівної цитати в зазначеному turn, можливі суперечності й бюджет. Результат приймається без обов'язкового ручного затвердження кожної відповіді. Записи версійовані, LLM evidence/read-only. Якщо на п'ятому питанні критерій не оцінено, залишаємо `null`. Два логічні агенти можуть використовувати одного provider та різні промпти; не впроваджуй дорогий мультиагентний framework.

### Matching і порядок вакансій

- Для альтернативи вимоги вакансії з критеріїв `D_vga`, цільових порогів `τ_vgad∈(0,1]` та `β_d>0`: за відомого `s_ad`, `h=min(1,s_ad/τ_vgad)`, за `null` є лише інтервал `h∈[0,1]`. Обчислюй `L` через вагову суму відомих `h`, поділену на вагу ВСІХ потрібних критеріїв; `U=L+невідома_вага/загальна_вага`.
- `OR`: `L_group=max(L_alt)` і `U_group=max(U_alt)`, не сума. `AND`: групи залишаються незалежними вимогами.
- Для обов'язкового критерію `τ`: `s≥τ` — виконано; `s<τ−min(.05,τ/2)` — не виконано; прикордонний стан і `null` — невирішено. Альтернатива `AND` за критеріями, група `OR` за альтернативами. `Z=2`: всі обов'язкові групи задоволено, `Z=1`: невирішені / відсутні явно обов'язкові, `Z=0`: хоч одна обов'язкова група точно не виконана.
- `X=2` якщо кандидат задовольняє явно мінімальний досвід, `X=1` якщо досвід не визначено, `X=0` якщо недостатній; не штрафуй за більший стаж.
- Усередині mandatory/preferred класів отримуй середні нижні межі `L^M,L^P` і невизначеності `W^M,W^P=U−L`. Для порожнього класу — нульові службові значення плюс explicit absent flag. За коректно визначених вимог sort **`(Z DESC, X DESC, L^M DESC, L^P DESC, W^M ASC, W^P ASC, stable vacancy ID ASC)`**. ID може бути UUID. Для відсутніх рубрик/порогів/неоцінних вакансій застосуй `NOT_EVALUABLE`/`LOW_INFORMATION` з окремим обґрунтуванням, не вигадуй значень. Прикордонні оцінки не можна перетворювати на безпідставне «виконано».
- `F/I` ринку — **для пріоритету інтерв'ю**, а не додатковий множник у fit вакансії. Будь-який `Score` — не probability. UI показує клас відповідності, сильні сторони, конкретні прогалини, невідомі критерії, оцінку досвіду та джерело оцінки.

## 4. Persist і API

Внеси **non-destructive Alembic migration**: профіль/самооцінки, професійні дії й концепти, рубрики/критерії/версії, targets із `EXPLICIT_TEXT` vs `POLICY_DERIVED`, frozen snapshot requirements, market profile, interview turns/action budgets, незмінні assessment revisions, profile versions, ranking evidence та ingestion provenance. Не скидай існуючі таблиці без міграції, збережи акаунти та 90 вакансій. Для старих рівнів 1/2/3 допускається лише прозора політика відображення `0.50/.75/.90` із `LEGACY_MIGRATION`, не видавай її за пороги, написані роботодавцем. ESCO URI не визначає поріг або рубрику. Не заповнюй професійні рубрики тільки випадковими прикладами; забезпеч осмислені anchors і походження кожного policy-derived rubric.

Створи мінімальні, логічні REST-маршрути для авто-cohort, market profile, interview (next/answer/pause/resume/finish), criterion assessments і ranked recommendations, а також керованого admin ingestion. Імена в `IMPLEMENTATION_SPEC.md` — **пропозиції**, не твердження про існуючі роутери: можеш зберігати сумісні існуючі назви. Обов'язкові: автентифікований ownership на кожному ресурсі, idempotency keys для відповідей/запитань, optimistic session version, зафіксована прив'язка assessment до rubric і snapshot, коректний `GET` після refresh.

## 5. Імпорт вакансій і питання без ручного величезного банку

Побудуй авторизований ingestion для JSON/CSV/вставленого тексту (без несанкціонованого скрейпінгу). LLM виділяє із вакансії метадані, обов'язкові/бажані групи, OR/AND, конкретні професійні дії та **точні фрагменти вихідного тексту**, які підтверджують кожну вимогу. Нормалізація: локальні aliases → завантажені дані ESCO / справжній API за наявності доступу → review неоднозначних кандидатів. Жодної вигаданої ESCO URI. Якщо ESCO недоступний, залишати unmapped і працювати з перевіреними локальними ID. Не видавай пусту таблицю pgvector за реальний semantic pipeline; embedding retrieval факультативний тільки за справжнього населення vectors. Дублікати/оновлення вакансій не повинні змінити вже заморожені знімки.

Генерація інтерв'ю запитань **динамічна** з професійної дії, рубрики й evidence-gap. Існуючі 120 запитань є лише резервом і матеріалом для дослідницького статичного режиму. Резерв без LLM має використовувати відкриті текстові відповіді та чесно лишати їх **неоціненими**, а не автоматично присвоювати компетентність.

## 6. Повний аудит React/української мови/UX

Перевір кожний екран, стан і кнопку: auth, welcome, profile edit, cohort empty/loading, interview, follow-ups, skipped/pending, pause/resume, results, market table, vacancy explanations, catalog after first results, account settings, delete/logout. Видали `u(...)`, перепиши всі тексти грамотною українською, включно з повідомленнями сервера. Ніяких банерів «MVP/демо», фальшивих успіхів, фальшивих вакансій з живими посиланнями чи невідомих англійських UI-слів. При цьому в інформації про джерело даних правдиво вкажи, що локальний посів вакансій є **синтетичним**, і не приписуй йому актуальності реального ринку. Плавні, короткі логічні анімації, з підтримкою `prefers-reduced-motion`. Responsive 320px–desktop, клавіатура, focus management, текстові підписи, accessibility, дієві error/loading/retry. До first-results не показувати багатотабовий кабінет, а після — показати. Самооцінка редагована, LLM-оцінка read-only, з поясненнями й без псевдоточних «100% fit».

## 7. Перевірки, обов'язкові тести, результат

Почни з конкретного інвентарю та baseline запуску тестів. Далі реалізуй і перевір щонайменше:

- **Математика:** N=0, порожні/дубльовані вимоги, нормування I, ринковий F і об'єднання parent, OR групи, Q monotone/submodular за фіксованого t, greedy ties і адаптивне перепланування, self-rating 0 vs unknown, 10×5 caps, діапазони rubric, zero/`null`, near-threshold ε, пороги τ<.05, L/U інваріанти, Z/X, missing mandatory class, tie UUID.
- **Backend:** реальний PostgreSQL із Alembic, idempotent seed, scope ownership, заморожені вимоги, повторне надсилання тієї самої відповіді, два одночасні запити, перерваний/відновлений діалог, неможливість редагувати LLM-оцінки з фронтенда.
- **LLM:** mocks на валідну оцінку, пропущені свідчення, некоректний JSON, retry/timeout/rate limit, узгоджене уточнення; окремо реально перевір API провайдера, якщо ключ наявний, не заявляючи цього без доказу.
- **Frontend:** TypeScript typecheck/build, повний проход auth → welcome → profile → auto cohort → open-text interview → rubric assessment → recommendations → market profile; responsive/keyboard/reduced motion.
- **Ingestion:** authorized import, schema/source quote validation, dedup, unmapped ESCO, offline ESCO, frozen snapshots unchanged.

Виконуй реальні команди (`cd app && uv sync && uv run pytest -q`, `cd app/frontend && npm install && npm run build`, `cd app && docker compose up --build -d`, Playwright/browser smoke якщо доступні). Перевір, що npm script `typecheck` існує, і додай його, якщо потрібний. `uv.lock` та npm lockfile створюй тільки через успішну установку залежностей. Не вигадуй ні результати тестів, ні наявність Docker/мережі/LLM credentials.

**Завершення:** у звіті напиши файли/міграції, які реально змінено; які сценарії працездатні; результати фактично запущених перевірок; блокери зовнішніх інтеграцій; що залишається експериментально оцінити (рекомендації, LLM vs незалежні експерти). Якщо робота занадто велика для одного проходу, спочатку забезпеч повністю працездатне основне коло (авто-cohort → інтерв'ю → критерії → ranking → UI), а потім ingestion і поглиблені polish-опції. **Не зупиняйся на документах; змінюй код.**
