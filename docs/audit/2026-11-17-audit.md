## I. Архітектура

1. **Відповідність розділам 2–3.** Модульний моноліт FastAPI + SQLAlchemy + чисті функції в `backend/domain/` відповідає. Не реалізовані описані компоненти: підсистема імпорту і виділення вимог LLM (розділ 2.4, 3.2), нормалізатор ESCO, оновлення словника, асинхронні завдання, три режими порівняння (початковий профіль / статичне / адаптивне). У коді немає жодного згадування ESCO чи extraction (пошук по `backend`, `scripts`, `alembic`); таблиця `competency_vectors` створена міграцією `alembic/versions/0001_initial.py:22-29`, але ніде не заповнюється й не читається.
2. **Шлях даних.** Фактичний: `scripts/generate_fixtures*.py` → `fixtures/vacancies.json` → `backend/seed.py` → таблиці `vacancies`/`requirement_groups`/`requirement_alternatives` → `cohorts.get_or_create_cohort` (`api/cohorts.py:52-69`, незмінний знімок з SHA-256) → `compute_market` (`domain/market.py:24`) → `planner_state`+`choose_next` (`domain/core_flow.py:53`, `domain/planner.py:28`) → Interviewer (LLM) → відповідь → Evaluator (LLM) → `criterion_assessments` → `_action_scores` (`api/core.py:54`) → `rank_vacancy` (`domain/core_flow.py:73`) → відповідь API. Етапів «текст вакансії → extraction → normalization» **немає**: структура вимог (групи, альтернативи, `required_level`) створена генератором фікстур.
3. **Детерміноване / LLM.** Детерміноване: знімок, ринок, планувальник, бюджет, пороги, ранжування. LLM: текст питання і оцінки критеріїв. Випадків, коли LLM вирішує те, що за дипломом вирішує алгоритм, немає: тема, бюджет і порядок визначаються Python. Виняток: `sufficient_evidence` і оцінку 0 для «не знаю» визначає LLM (`domain/interview_budget.py:19-26` лише довіряє цим полям).
4. **Шари.** Домен чистий (`domain/*`), HTTP і оркестрація змішані: `api/core.py` містить і HTTP, і логіку вибору теми (`core.py:196-224`), і виклик LLM усередині транзакції (`core.py:338`). Окремого шару репозиторіїв немає, запити SQLAlchemy розсіяні по роутерах.
5. **Тестованість без FastAPI/БД/LLM.** Ranking, matching, market, planner, budget, assessment тестуються як чисті функції (`tests/test_ranking.py`, `test_criteria.py`, `test_core_flow.py`, `test_planner.py`, `test_market.py`). Вибір наступної теми в `api/core.py:196-224` не винесений в чисту функцію і тестується лише через HTTP.
6. **Приховані залежності.** (а) `latest_scores(db, user)` (`api/core.py:67-71`) об'єднує оцінки всіх інтерв'ю користувача незалежно від профілю й спроби; використовується застарілим `POST /recommendations` (`api/recommendations.py:49`). (б) `User.track` має значення за замовчуванням `python` (`models.py:23`). (в) Ранжування не зберігається (немає `RankingRun`): результат обчислюється щоразу з поточних констант (`TAU_BY_LEVEL`), тому зміна порогів змінює старі результати. (г) `source_label` бере поле з БД наживо (`api/recommendations.py:33`).

## II. Вакансії і профіль ринку

7. **Походження вакансій.** Усі 180 записів синтетичні: `scripts/generate_fixtures_v2.py:8` — «invented (source_type SYNTHETIC_GENERATED); nothing is scraped or copied from job boards»; у JSON 90 `DEMO_CURATED` і 90 `SYNTHETIC_GENERATED`. При цьому **інтерфейс для всіх підписує джерело «Djinni»** (`api/common.py:46-48`, зміна за вказівкою власника, не перевірена). Це розбіжність з даними і з вимогою чесності даних. Розділ 3.5 називає 90 записів, у репозиторії 180.
8. **Походження.** Зберігаються `source_type`, `source_url` (завжди `null`), `fixture_version` (`models.py:81-83`) і `RequirementGroup.excerpt` на рівні групи. Немає тексту оголошення, дати отримання, хешу вмісту, версії правил, фрагмента на рівні альтернативи (`models.py:107-114`). Вимоги диплому з 3.2 не виконані (**Н**).
9. **Типи вимог.** `kind` = `MANDATORY`/`DESIRED` (1234/546), групи з однією, двома і трьома альтернативами (1541/219/20). «FastAPI або Django» — одна група з двома альтернативами. Але розпізнавання робить генератор, не система (**Ч**).
10. **OR не стає AND.** `eval_group` (`domain/core_flow.py:30-50`) бере максимум меж, SATISFIED при будь-якій виконаній альтернативі, FAILED лише коли всі провалені. Перевірено запуском: `{fastapi:0.9, django:0.1}` → SATISFIED, `{0.1, 0.1}` → FAILED, `{0.1, None}` → UNRESOLVED з відкритою альтернативою `django`. Тести `tests/test_core_flow.py:9-19`. **Р**.
11. **ESCO.** **Н**. Поле `normalization_status` — константа `ACCEPTED_CURATED` (`models.py:111`), URI ESCO у моделі `Competency` немає (`models.py:53-61`), різниця синонім/ширше/вужче не моделюється.
12. **Вигадування URI.** Неможливе, бо URI немає взагалі. Поведінка при недоступності ESCO не визначена, бо сервісу немає.
13. **F(c), формула (2.2).** `domain/market.py:44-45`: вакансія рахується один раз через множину `present`; знаменник N — лише вакансії з групами (`:30`). Тест `tests/test_market.py:4` (`test_repeated_mention_counts_once`). **Р**.
14. **I(c), формула (2.3).** `market.py:41-43`: вага групи `1/(N·|G_v|)`, ділиться порівну між унікальними альтернативами. Запуск: сума I = 1,000000; повторення дії в трьох групах однієї вакансії дає F=1. Тест `test_mass_sums_to_one`. **Р**.
15. **Ринкові ваги лише для планування.** `rank_vacancy` приймає `scores` і `user_years`, I(c) не використовується (`core_flow.py:73-92`); I(c) входить тільки як tie-break планувальника (`api/core.py:203`). **Р**.

## IV. Адаптивне інтерв'ювання

34. **Алгоритм.** Реальний жадібний вибір за приростом покриття (2.4–2.5): `core.py:198`, `planner.py:28-56`. Не сортування за частотою.
35. **A_open.** Перераховується після кожної відповіді з `attempt_scores` (`core.py:198`). Група, у якої одна альтернатива виконана, закрита; прострочена альтернатива не відкрита (`core_flow.py:40`).
36. **Tie-breakers.** Обов'язкові групи: так. Самооцінка: **ні** (порожня множина). I(c): так (`core.py:203`). Стабільний id: так.
37. **Адаптивність.** Контрольний запуск (дві вакансії, чотири теми): без оцінок → `sql`; fastapi сильний → `sql`; fastapi + sql виконані → `kafka`. Тест на розбіжність двох сценаріїв на рівні API відсутній (є тільки функціональні тести планувальника).
38. **Обмеження.** До 10 тем і 5 питань працюють (`interview_budget.py`, тести). Раннє закриття теми: достатні докази і оцінка ≥0,75 або ≤0,05. Відхилення від диплому: за достатніх, але середніх доказів (наприклад 0,5, `sufficient=true`) код все одно вимагає друге питання (`interview_budget.py:24-26`).
39. **Уточнення.** Interviewer отримує назву дії, опис, **усі** ідентифікатори критеріїв рубрики (`criteria_for`, `core.py:238`), останні відповіді, рівень. `followup_goal` завжди `None` (`core.py:241`): поле `followup_goal`/`needs_followup` схеми Evaluator (`assessment.py:28-29`) не читається ніде. Вимога 3.2 «конкретна ціль уточнення» **не виконана**.
40. **Складність за рівнем.** Є лише в промпті (`agents/prompts.py`, `candidate_level.resolve_level`). Формалізації в математичній моделі немає. Потрібно визначити: як рівень кандидата змінює τ або вибір критеріїв, чи це лише стиль питання.

## VI. Надійність і безпека

49. Знімок незмінний: ревізії вимог копіюються в `CohortSnapshot.requirement_revisions` (`cohorts.py:63-66`). Оновлення каталогу не змінює відкрите інтерв'ю. Окремої таблиці версій вакансій немає, живі записи змінюються на місці (`seed.py` синхронізує назву наживо).
50. Ідемпотентність: повтор з тим самим ключем повертає раніше збережену відповідь (`core.py:317-320`), унікальні обмеження в `models.py:327-328`. Гонка двох «наступне питання» тепер повертає питання-переможця. Повтор після таймауту LLM: відповідь не збережена, див. 51.
51. **Проблема.** `submit_answer`: `db.flush()` (`core.py:334`) → `_assess_action` (виклик LLM, може тривати хвилини, `core.py:338`) → `db.commit()` (`:339`). Відповідь не фіксується до завершення оцінювання, що суперечить 3.2 («відповідь зберігається до виклику Evaluator»); транзакція утримується на весь час виклику. Відновлення призупиненого інтерв'ю працює (питання не регенерується, бюджет за збереженими ходами).
52. Усі інтерв'ю, профілі, знімки, оцінки перевіряють власника (`_owned_*`, `api/core.py:29-40`, `profiles.py`), тести `test_owner_isolation`, `test_cohort_scoped_to_owner`. Каталог і ринок публічні за задумом. Захисту від перебору паролів і обмеження частоти запитів не виявлено (**НП** повністю).
53. Відповіді кандидата екрануються й обгортаються тегами (`agents/prompts.py:121-126`), правило «дані, не інструкції» є в обох промптах. Текст вакансії до LLM не потрапляє взагалі. Тести на інʼєкції структурні, живої перевірки стійкості немає.
54. **Ч.** `DELETE /profile/data` (`api/profile.py:80-87`) видаляє оцінки, інтерв'ю, знімки, самооцінки, але не `User`, не `CandidateProfile` (ім'я, локація, посада, роки), не застарілі таблиці (`InterviewSession`, `MatchRun`, `ProfileVersion`, `EvidenceItem`). `DELETE /profiles/{id}` лише архівує (`api/profiles.py:100`). Інтерфейс цих викликів не робить.
55. Помилка LLM не створює оцінок: `UNGRADED` без рядків (`core.py:276-289`), питання з банку позначені `FALLBACK_UNGRADED`. Але тема після цього закривається без оцінки (відповідь втрачається для рейтингу).

## VII. Тестування і наукова достовірність

59. Precision@5, NDCG@10: коду немає (пошук по репозиторію не знайшов).
60. Зараз реально вимірюється: кількість питань (10 тем, у прогоні 14 питань), частка резервних питань, затримка викликів LLM, покриття груп. Потребують даних: F1 виділення (немає виділення), точність ESCO (немає ESCO), MAE оцінювача (потрібні експертні оцінки), Precision@5 і NDCG@10 (потрібна експертна релевантність).
61. Не вистачає: еталонної експертної розмітки (оцінки відповідей, релевантність вакансій), реальних вакансій з дозволом на використання, реалізації імпорту/виділення/ESCO, реалізації трьох режимів, фіксації моделі й промпта, незалежного тесту оцінювача.

### D. Тести, які треба додати першими

1. Властивісний тест: нова оцінка не розширює [L,U], завжди 0≤L≤U≤1 (hypothesis).
2. Тест «1 із 5 критеріїв» не закриває обов'язкову групу.
3. Тест: бал без доказів і неповний набір критеріїв відхиляються.
4. Тест порядку продукту проти (2.15): Z=0 з великим відсотком не вище за Z≥1.
5. Контрольний тест двох сценаріїв: однаковий профіль, різні відповіді → різні наступні теми (інтеграційний).
6. Тест: самооцінка бере участь у tie-break і не закриває групу.
7. Тест: відповідь зберігається, якщо LLM впав або перевищив час.
8. Тест: `followup_goal` оцінювача потрапляє в наступний виклик Interviewer.
9. Тест H(v,p): формат роботи та локація кандидата.
10. Контрактний тест рубрик: кожна дія має рубрику, критерії унікальні, bands повні.
11. Тест відтворюваності: однаковий знімок і оцінки → однаковий порядок після зміни констант (версія політики).
12. Тест видалення: після видалення даних не лишається персональних записів.
13. Каркас метрик: Precision@5, NDCG@10 на розміченому наборі (еталон незалежний від системи).

### F. Оцінки

- **Відповідність дипломній математичній моделі: 4 з 10.** Доведено запусками: формули ринку, h, ε, OR-логіка, Z/X, ключ (2.15) у домені, жадібний вибір теми. Знижують оцінку: M_c замість s_cd, відсутність E_c, D_vga, T_v/J_v, мертва перевірка самооцінки, продуктове сортування за відсотком, відсутні імпорт/ESCO/режими/метрики.
- **Технічна і алгоритмічна обґрунтованість самої системи: 5 з 10.** Чистий домен, детерміноване ядро, власність даних, ідемпотентність, знімки, добрий набір арифметичних тестів. Знижують оцінку: оцінка рівня без калібровки і без еталона, відповідь і LLM в одній транзакції, відсутнє походження оцінок, жорсткі пороги, синтетичні дані з підписом реальних, неповна валідація виходу LLM.

Вищі бали не підтверджені: немає ні експертної розмітки, ні вимірювань точності оцінювача чи якості ранжування.
