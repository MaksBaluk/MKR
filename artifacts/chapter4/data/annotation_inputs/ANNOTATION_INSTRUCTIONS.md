# Інструкція для незалежної анотації (протокол v2, pool-v1)

Статус: **анотацію не виконано.** Файли `data/annotations/*.csv` містять лише заголовки. Анотацію виконують окремі «свіжі» агенти з міткою `LLM_ANNOTATOR_PILOT` (не експерти) або люди-експерти (`HUMAN_EXPERT_<n>`). Укладач стенду (агент, що будував експеримент) не анотує.

## 1. Незалежність

Анотатор отримує **лише**:

- `candidate_descriptions.jsonl` — опис компетентностей кандидата, незалежний від виходу CompetenceMatch;
- `vacancy_texts.jsonl` — назва, рівень, мінімальний досвід і тексти вимог вакансії;
- `vacancy_pool.csv` — фіксований пул вакансій для кожного кандидата (у випадковому порядку);
- `criterion_items.jsonl` — питання і відповідь (для оцінювання критеріїв), разом із назвами критеріїв рубрики `v1` (`app/fixtures/rubrics.json`).

Анотатор **не бачить**: `data/hidden/`, `raw/`, `experiment_runs.csv`, `ranking_results.csv`, `seniority_results.csv`, будь-який рейтинг, оцінку чи рівень системи, назву сценарію, «запланований рівень». Анотатор не може бути тією самою моделлю/заглушкою, що виконує роль Evaluator у прогонах. Два проходи (`LLM_ANNOTATOR_1`, `LLM_ANNOTATOR_2`) виконуються незалежно, без доступу до результатів один одного.

Обмеження, яке треба вказувати в тексті: LLM-анотатори корельовані з LLM-оцінювачами; їхні мітки — пілотні й не доводять точності на реальних кандидатах. Відповіді в `criterion_items.jsonl` є шаблонними фразами симулятора: оцінювання критеріїв за ними перевіряє узгодженість шкали, а не якість реального Evaluator.

## 2. Релевантність вакансії (шкала визначена до анотації, `scale_version = rel-0-3/v1`)

Оцінюється відповідність **описаного** кандидата вимогам вакансії (не бажання кандидата і не престиж вакансії).

| Оцінка | Визначення |
|---|---|
| 3 | Усі обов'язкові вимоги покрито впевненим або практичним рівнем; рівень вакансії відповідає рівню кандидата. |
| 2 | Більшість обов'язкових вимог покрито; не більше однієї суттєвої прогалини або рівень вакансії на один крок вищий/нижчий. |
| 1 | Покрито менше половини обов'язкових вимог або є кілька суттєвих прогалин; можлива лише як «ріст». |
| 0 | Ключові обов'язкові вимоги не покрито («не працював»/«лише чув») або рівень явно не відповідає. |

Для P@5 релевантною вважається оцінка ≥ 2. NDCG@10 використовує оцінку 0–3 як gain. Кожна пара (кандидат, вакансія) з `vacancy_pool.csv` отримує оцінку; пропуск не дозволено (якщо неможливо оцінити — `relevance` порожнє і `rationale` пояснює причину; такий рядок не входить у метрики).

## 3. Рівень кандидата (`expert_seniority.csv`)

Значення: `JUNIOR`, `MIDDLE`, `SENIOR`, `UNKNOWN`. `UNKNOWN` = доказів недостатньо, щоб відповідально визначити рівень (не синонім Junior). Рівень **не визначається роками досвіду чи бажаним рівнем**.

- JUNIOR: базові навички мови, SQL, тестування, контроль версій підтверджено практикою; самостійність у типових задачах.
- MIDDLE: додатково — ефективні запити, узгодженість даних, проєктування сервісів, тестова ізоляція, конфігурація розгортання; обґрунтовує рішення, діагностує проблеми.
- SENIOR: додатково — експлуатація БД і міграції, конкурентність, гарантії доставки, безпека доступу, діагностика інцидентів, еволюція контрактів; компроміси, невизначеність, відповідальність за результат.

Приклади: «12 років досвіду, усе на рівні "розуміє загальну ідею"» → не Senior (UNKNOWN або JUNIOR за доказами). «Бажає Junior, але впевнено описує експлуатацію БД, міграції, інциденти» → SENIOR. «Сильний у двох темах, інші не описано» → UNKNOWN, якщо цього недостатньо для будь-якого рівня.

## 4. Оцінка критерію (`expert_criterion_annotations.csv`)

`score` ∈ [0, 1] за якорями рубрики (0 — немає/неправильно; ~0.3 — лише чув; ~0.6 — загальне розуміння; ~0.78 — застосовував; ~0.9 — пояснює механізм на прикладі) або порожньо, якщо відповідь не містить свідчень щодо критерію (`evidence_status = NO_EVIDENCE`). Інакше `evidence_status = EVIDENCED`. Не приписувати оцінку критерію, про який відповідь не говорить.

## 5. Узгодження (adjudication)

1. Після двох незалежних проходів обчислити розбіжності: релевантність — |r1 − r2| ≥ 2 або різна сторона порогу 2; рівень — будь-яка різниця; критерій — |s1 − s2| > 0.2 або один порожній.
2. Збіги й розбіжності ≤ 1 бала (релевантність) записуються як `annotator_id = ADJUDICATED` з округленим униз середнім (релевантність) / середнім (критерій) / спільним значенням (рівень).
3. Решту розглядає третій незалежний прохід (`LLM_ANNOTATOR_3` або експерт), бачачи обидві мітки та їхні обґрунтування, але не вихід системи; його рішення → `ADJUDICATED`, з поясненням у `rationale`.
4. Звітувати узгодженість до узгодження: зважена каппа Коена (релевантність, рівень), MAE між проходами (критерії).

## 6. Обсяг і статистична потужність

Пул: див. `vacancy_pool.csv` (об'єднання Top-10 усіх режимів/бюджетів/сідів + 10 стратифікованих випадкових вакансій когорти на кандидата). Кандидатів 18. Одиниця аналізу — кандидат. Для парного порівняння двох режимів знаковим тестом при n = 18 двобічний p < 0.05 досягається лише при ≥ 14 з 18 однакових за напрямом відмінностей (без нічиїх); менші ефекти не виявляються. Тому висновки з пілотної анотації — описові (статус PILOT), без тверджень про статистичну значущість.
