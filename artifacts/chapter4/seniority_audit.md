## 2. Незалежність величин (2.1)

Детально — `architecture_audit.md` §2–3. Коротко: `estimate(policy, evidence)` не має параметрів бажаного рівня, років, посади, самооцінки чи вакансій (a; `math_checks` S01, S04; сценарії S01, S07, S08). Бажаний рівень задає лише складність першого питання (`difficulty/v2`) і зберігається як мітка. Estimator і Matching читають ті самі ефективні бали однієї спроби; різняться лише пороги (τ_L рівня проти τ вимоги вакансії).

## 4. Чому Senior складний: фактичні причини пропусків

Перевірено інспекцією всіх 26 пропущених шумових прогонів (`raw/seniority_sweep_runs.csv`, колонки `senior_reasons`, `causes`, `fallback_questions`, `senior_members_never_targeted`).

| Причина | Частка | Чи є це властивістю продукту |
|---|---|---|
| `TECHNICAL_POOLS_BELOW_MIN` (2–3 технічні пули Senior замість 4) | 25/26 | так, наслідок нижче |
| банкові питання без оцінки в темах kafka і ci-cd | 26/26 (сер. 7.8 питання) | **ні — артефакт стенду**: заглушка пише складність англійською «(advanced)»; з однією назвою критерію і латинськими «Apache Kafka», «CI/CD» частка кирилиці < 0.7, продукт відхиляє питання (`backend/agents/graphs.py:150`, `NOT_UKRAINIAN`) і ставить банкове питання без оцінки. За 2 крит./пит. кирилиці достатньо. Задокументоване в MATH_SPEC пояснення «англійські назви критеріїв» неточне: назви критеріїв українські (`fixtures/rubrics.json`) |
| тему postgresql не обрано (`REQUIRED_CAPABILITY_UNCONFIRMED`) | 9/26 | лише разом з артефактом (у варіанті — 0) |
| `profile = senior-no-aws` | 14/26 | частково продукт: без AWS лишається менше альтернатив для «Безпека доступу» і «Вартість і надійність» |

**Контрольний прогін зі зміненою заглушкою** (`--stub-ua`, `realistic_runs.UaModel`: лише слово складності українською; продукт, шум, сіди, профілі ті самі; 224 інтерв'ю, 4 хв 38 с): хибний Senior **0/112**, хибний Middle+ 0/56, пропущено Senior **14/112** (1 крит./пит. 14/56, 2 крит./пит. 0/56), пропущено Middle 0/56, банкових питань 0, postgresql обрано у 224/224. Отже ≈12 з 26 пропусків спричинені стендом, а не продуктом. Решта 14: 13 із них — цілі GAP_ONLY за 1 крит./пит. (Evaluator вимагає повторити слабкий критерій, тема вичерпує 5 питань до Senior-критеріїв), 7 — профіль без AWS; у кожному лише 2–3 технічні пули Senior.

Перевірка гіпотез специфікації 2.3:

| Гіпотеза | Висновок |
|---|---|
| забагато критичних критеріїв | частково: Senior має 9 технічних пулів, з них ≥4 треба підтвердити; на когорті python з 10 тем зазвичай досяжні 7 (`concurrency` і `incident-diagnosis` Q_t не обирає — `MATH_SPEC` §3e v2) |
| бюджет | так для 1 крит./пит.: ≤5 питань на тему недостатньо для 9–10 критеріїв теми postgresql |
| раннє закриття тем | ні: продовження за рівнем тримає тему; обмежує лише ліміт 5 |
| пороги | не основна причина: за 2 крит./пит. 0/56 пропусків при тих самих τ |
| трактування UNKNOWN | коректне: UNKNOWN не є прогалиною; але й не заповнює мінімум — це свідомо |
| вимога підтвердити всі технології | ні: пули крос-інструментальні, «немає досвіду» з інструментом не є прогалиною, поки альтернативу не питали (крім жорстких пулів — див. NR-1) |
| розподіл критеріїв рівнів | так: обидва обов'язкові пули шару даних Senior (`db-operations`, `schema-migrations`) досяжні лише через postgresql/django; за WS-1 кожен потребує двох незалежних підтверджень |
| циклічна залежність рівень ↔ складність | не виявлено в `difficulty/v2`: складність стартує з бажаного рівня лише для першого питання й далі слідує відповідям |

Пороги не знижувалися. Обґрунтоване рішення (пропозиція, не реалізовано): у `level_probe` ставити критерії пулів Senior, яких бракує до `T^min`, вище за повтори GAP_ONLY-цілі в межах тих самих 5 питань; і для фази 2 використовувати заглушку без артефакту `NOT_UKRAINIAN` або явно звітувати обидва варіанти.

У v4 немає стану з назвою FAILED: його роль виконує `GAP`; специфікаційне «UNKNOWN» для рівня = `UNVERIFIED`. Обмеження UI — `architecture_audit.md` A-5.

## 6. Професійне мислення (2.4)

Шість практичних критеріїв `practice-backend.{independence, rationale, tradeoffs, diagnosis, ambiguity, ownership}` (`fixtures/practice_rubrics.json`, `v1`, `CURATED_TEMPLATE`) мають поведінкові якорі за п'ятьма смугами (напр., `diagnosis`: «конкретні перевірки без порядку» = [.5,.75)). Особистість, стиль мовлення чи впевненість не оцінюються. Бал практики проходить ту саму валідацію, що й тематичний: id з дозволеного списку, дослівна цитата відповіді; одна невалідна позиція відхиляє весь вихід (§3d). Рівень бере медіану балів по темах-джерелах (v4). Вимоги політики: Junior — 0 пулів практики, Middle — ≥2 з {independence, rationale, diagnosis}, Senior — ≥3 з {tradeoffs, ambiguity, ownership, diagnosis, rationale}.

**Знахідка S09 (суперечність зі специфікацією, не виправлялась).** `practice-backend.independence` не входить до пулів Senior і не обов'язкова для Middle (досить rationale + diagnosis). Тому сильні технічні відповіді + інші п'ять аспектів практики без жодного доказу самостійності дають **SENIOR** (`seniority_results.csv` S09, FAIL відносно буквального очікування). Без жодної практики — JUNIOR (S09a, PASS). Це рішення змісту політики, а не порогів; потрібне рішення власника/експертів, чи є самостійність обов'язковою для Senior.
