Код: `282f6fb`. Метод: читання коду з посиланнями `файл:рядок`, пошук використань (`grep`), детерміновані проби й тести фази 1. Продуктовий код не змінювався. Дефекти — у розділі 5 (P0/P1/P2).

## 1. Потік даних (фактичний)

```
профіль (target_level, desired_title, years, self-ratings)
  └─ POST /cohorts/auto ─ H(v,p) = track + is_active (cohorts.py:21) ─ знімок когорти (vacancy ids, D_vga, τ, sha256)
       └─ POST /interviews ─ start_desired_level, start_policy_* (міграція 0017)
            └─ next-question: Q_t (planner.choose_next) → тема; level_probe (порядок критеріїв, продовження, підказки практики);
               difficulty/v2 (рівень питання); Interviewer (LLM-роль) — питання; validate_question
            └─ answers: Evaluator (LLM-роль) → validate_against_context → criterion_assessments (ревізії, no_experience)
            └─ finish → finalize_on_finish → seniority_assessments (незмінний рядок на (спробу, версію політики))
  GET /profiles/{id}/results ─ attempt_scores(спроба) → rank_items (2.15+T/J+id) → сортування за confirmed_share (екран)
  GET /interviews/{id}/level ─ рядок seniority_assessments → level_payload (назви українською)
```

## 2. Незалежність `desired_level`, `assessed_level`, `vacancy_fit`

| Перевірка | Результат | Доказ |
|---|---|---|
| Входи оцінювача рівня | лише `(policy, evidence)` | `seniority.py:283`; `math_checks` S01 (сигнатура + `finalize_level` передає тільки `attempt_evidence`, `level.py:67`); тест `test_desired_level_years_and_self_rating_are_not_estimator_inputs` |
| `desired_level` у рядку рівня | лише мітка (`start_desired_level`, інакше профіль) | `level.py:75-76` |
| Вплив `desired_level`, `desired_title`, `years` на потік | лише складність **першого** питання спроби (`difficulty/v2`) і «обстановка» питання в промпті Interviewer (`prompts.py:61-63`, `candidate_level`, `years_experience`); Evaluator їх не отримує | `core.py:465-477`, `core.py:616-621`, `prompts.py:206-218` |
| Роки / посада як доказ | ні; `candidate_level(desired_title, years)` використовується тільки як апріорна складність, коли `target_level` порожній | `candidate_level.py:14-30` |
| Самооцінка | не вхід оцінювача; у ранжуванні тільки `T_v/J_v` для точних нічиїх; планувальнику — `needs_verification` (пріоритет питання) | `math_checks` T01, S04 |
| Рівень → ранжування | ні: `rank_items` не читає рівень; секції результатів (`_section`) — мітки над незмінним порядком | `profiles.py:233-237`, `MATH_SPEC` §3e «Not affected» |
| Адверсарні проби | S01 (desired senior, лише база → JUNIOR), S07 (desired junior, докази Senior → SENIOR, також E2E), S08 (15 років, слабкі відповіді → UNKNOWN, також E2E) | `seniority_results.csv` |

Висновок: три величини розділені. Залишковий канал — апріорна складність першого питання і обстановка питань; вплив на рівень лише опосередкований (через питання, а не через оцінку). Знайдено один недолік узгодженості: `_level_context` читає **поточний** профіль (`core.py:617-621`), а не старт-знімок спроби; якщо профіль змінено між створенням спроби і першим питанням, складність першого питання відповідатиме новому значенню (P2).

## 3. Одні й ті самі оцінки критеріїв для Estimator і Matching

| Аспект | Matching (`attempt_scores`) | Estimator (`attempt_evidence`) | Суперечність? |
|---|---|---|---|
| Джерело | `criterion_assessments` однієї спроби | ті самі рядки однієї спроби | ні |
| Поточний бал тематичного критерію | `effective_rows`: остання ревізія з балом | той самий `effective_rows` | ні |
| Практичні критерії | у словнику є, але вимоги вакансій їх не містять → не впливають | медіана балів по темах-джерелах (v4) | ні (різні призначення, задокументовано §3e) |
| Поріг | τ альтернативи вимоги (робоча карта .50/.75/.90, ε) | τ_L рівня (.50/.70/.75), межа прогалини .50 | різні питання до тих самих балів; бал 0.72 підтверджує Middle-пул, але для вимоги рівня 2 (τ .75) — `UNRESOLVED`. Не суперечність, але це треба пояснити в розділі 2 |
| Вимога цитати | ні (бал без цитати не проходить валідацію, тож на практиці завжди є) | так (`T_c ≠ ∅`), для реплікованих пулів — 2 різні відповіді | сумісно |

Висновок: обидва модулі читають один набір оцінених критеріїв однієї спроби; розбіжність лише в порогах, що задокументовано як різні рішення.

## 4. Шлях до API і UI: «Middle підтверджено, Senior не перевірено» vs «Senior перевірено, критичні прогалини»

| Ознака | S10 (не перевірено) | S12 (перевірено, прогалина) | Де |
|---|---|---|---|
| `assessed_level` | MIDDLE | MIDDLE | обидва |
| `coverage_by_level.SENIOR.status` | `UNVERIFIED` | `GAP` | API (`level.py:124-137`) |
| `reasons` | `CONFIRMED_COUNT_BELOW_MIN`, `TECHNICAL_POOLS_BELOW_MIN`, … | `CRITICAL_GAP` (+ `hard_gaps`) | API |
| Пояснення | «…Для висновку про Senior недостатньо даних.» | «…Для Senior виявлено критичні прогалини: «Експлуатація бази даних»…» | API `explanation`, UI `LevelSummary.tsx:72-75` |
| Списки UI | «Не перевірено» (назви пулів) | «Прогалини» | `LevelSummary.tsx:78-88` |

Перевірено тестом `test_s10_and_s12_are_distinguishable_in_the_result` і E2E-сценарієм `S10-E2E` (payload `SENIOR.status = UNVERIFIED`). Обмеження UI (P2): (а) стан кожного рівня (`status`) не показано явно — розрізнення тримається на тексті пояснення і на тому, у якому списку опинився критерій; (б) список «Прогалини» об'єднує прогалини всіх рівнів у межах звіту і толеровані прогалини без позначки рівня; (в) UI-перевірки цього розрізнення в Playwright немає (`level.spec.ts` перевіряє бажаний/оцінений рівень і секції).
